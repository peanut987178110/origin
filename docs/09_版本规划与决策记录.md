# 09 · 版本规划与关键决策记录（ADR）

> 这份文档回答面试里最难的一类问题：
> **"你为什么不做 X？"**
>
> 大多数候选人只能说"我觉得用不上"。真正做过产品的人能给出一条**被否决的方案**、
> 一个**当时的取舍理由**、以及一个**何时重新评估的触发条件**。

---

## 第一部分 · 版本路线图

### 1.1 总览

> ⚠️ **先看这一行**：下表区分「**已交付**」（真跑起来的代码）和「**待验证**」（产品假设）。
> 混着写是这类文档最容易出的问题——把计划当成绩讲，面试官一问细节就露馅。

| 版本 | 目标 | 核心验证 | 状态 | 成功标准 |
|---|---|---|---|---|
| **V0.1 内部原型** | 跑通链路 | 工作流能走通 | ✅ 已完成 | 12 节点全部连通 |
| **V1.0 规则引擎 Demo** | 验证"产品逻辑对不对" | 分支与边界能跑通 | ✅ 已完成（已废弃） | 词表覆盖的场景可演示 |
| **V2.0 真实产品** | 验证"愿不愿说" | H1 | ✅ 已交付（本地 Ollama） | 深度情绪表达占比 ≥ 20% |
| **V3.0 手机直连** | 让产品能真正被用 | 用户不需要电脑 | ✅ 已交付 v3.1.0 | 装上后 3 分钟内能聊起来 |
| **V3.5** | 验证"记忆值不值钱" | H2 / H3 | ⏳ 待验证 | 有记忆组 7 日留存比无记忆组高 ≥ 8pt |
| **V4.0** | 验证付费意愿 | H4 | ⏳ 待验证 | 付费转化 ≥ 5% |

**已经交付的东西**（不是计划，是能装的包）：

```
dist\潮汐Tide-v3.1.0.apk
  · 12 个角色 / 6 个人群分组
  · 9 家模型服务商（OpenAI 兼容协议）
  · 语音输入 + 语音朗读
  · 长期记忆（每 4 轮提炼）
  · 危机硬规则 + 记忆陷阱硬规则
  · API Key 加密存储、只进不出
```

**还没有的东西**（别在面试里说成有）：

```
· 没有服务器，账号换手机就没了
· 没有真实用户数据，留存/付费全是待验证假设
· 没有评测集跑分（evalset/ 里的结果是 MOCK）
```

### 1.2 V1.0 当初的范围（一句话）

> **只验证一件事：用户愿不愿意在深夜对 AI 说真话。**
> 其他一切都为这件事让路。

**V1.0 当时主动放弃**：语音、主动推送、多角色、情绪曲线、付费墙。

> 为什么敢砍这么狠？因为如果 H1 不成立——用户根本不愿意对 AI 说真话——
> 那语音做得再好、情绪曲线再漂亮，都是零。**先证伪最贵的假设。**

### 1.3 后来被打脸的部分（诚实记录）

V1.0 的取舍在纸面上是对的，但**实际推进时被推翻了两次**：

| 当初的决策 | 后来怎么变 | 为什么变 |
|---|---|---|
| 不做语音（ADR-01） | V2 就做了语音输入 + TTS 朗读 | 系统 TTS 是免费的、不联网的，成本远低于当初估的"ASR→LLM→TTS 5 秒延迟" |
| 不做多角色 | V3 做了 12 个角色 | 单一角色的「潮汐」聊起来像客服。**角色是"人味"的载体，不是功能堆叠** |
| 模型跑在用户电脑上 | V3 改成手机直连云端 | 手机上用产品，却要求电脑开着——这不是产品，是开发环境 |

> **面试怎么讲这一段**（比只讲计划强得多）：
> 「我 V1 定的范围是纯文本、单角色、不做语音。后来三个都推翻了。
> 语音是因为我错估了成本——系统 TTS 免费且不联网，我以为要接云语音。
> 多角色是因为实测下来单角色太像客服，用户不会对一个"工具"说真话。
> 最打脸的是第三点：我让模型跑在用户电脑上，然后跟人说'你装个 App 吧'——
> 那不是产品，那是把我的开发环境包装成了产品。
> **这三次推翻教会我一件事：砍范围要砍"验证不了的东西"，不是砍"用户要的东西"。**」

> 格式：决策 → 备选 → 选择 → 理由 → 代价 → 何时重估
> 每条都按面试能直接讲的颗粒度写。

### ADR-01 · 为什么做纯文本，不做语音

> 🔄 **已被推翻（V2 起）**：现在有语音输入 + 语音朗读。
> 推翻原因见 §1.3——当初把语音成本估成了"接云语音 + 5 秒延迟"，
> 实际用系统 TTS / 系统识别就够，免费、不联网、零延迟成本。
> **下面这条 ADR 保留原文，因为它的推理框架仍然成立（先证伪最贵的假设），
> 只是当时的成本估算错了。面试讲的时候要连着这个更正一起讲。**

| 项 | 内容 |
|---|---|
| **备选** | A. 纯文本 ｜ B. 文本 + 语音输入 ｜ C. 语音优先 |
| **选择** | **A（V1.0）** |
| **理由** | ① **延迟**：语音涉及 ASR → LLM → TTS 三段，实测行业普遍 4–6s，而陪伴场景的"停顿"本身就是体验的一部分，慢 2 秒就从"温柔"变"卡顿"<br>② **能力**：语音情感识别（语调/语速/哽咽）目前准确率不足以支撑"听出你没说出口的情绪"这个卖点，做了反而增加误判<br>③ **验证目标错位**：V1 要验证的是"愿不愿说"，文字链路成本最低、迭代最快 |
| **代价** | 语音是陪伴产品公认的体验分水岭（Pi、Replika 都靠它拉留存）。**不做等于放弃一部分人**——尤其是不想打字的人 |
| **重估条件** | 文字链路的 W1 留存 ≥ 25%【目标】后启动 V1.5 |
| **面试怎么讲** | 「我知道语音是陪伴产品的标配，Pi 就是靠这个起来的。但我 V1 不做，原因是当时要验证的是'愿不愿说'而不是'说得爽不爽'。语音会让首字延迟从 1.2 秒涨到 5 秒以上，而我还没有证据表明用户愿意忍这个延迟。」 |

### ADR-02 · 为什么做"工作流为骨架"，而不是纯 Agent

| 项 | 内容 |
|---|---|
| **备选** | A. 纯工作流 ｜ B. 纯 Agent（模型自主规划） ｜ C. 工作流骨架 + Agent 关节 |
| **选择** | **C** |
| **理由** | ① **安全不可交给模型自己决定**：危机识别必须走硬路由，让模型"自己判断要不要转危机分支"是不可接受的风险<br>② **可观测性**：纯 Agent 出问题时无法定位是哪一步坏了；工作流每个节点可单独评测<br>③ **成本**：Agent 多次循环调用，单轮成本可翻 3–5 倍 |
| **代价** | 工作流的固定路径覆盖不了没预设的情况，遇到新场景只能"接不住"，体验有天花板 |
| **重估条件** | 当某类 Badcase 连续 2 个版本都归因为"路径没设计到"，把该环节交给 Agent 节点自主处理 |
| **面试怎么讲** | 「我不会把'要不要拦住用户'这种事交给模型自主决定。安全是路由，不是判断。但生成环节我允许模型自己决定调不调工具——**骨架是我的，关节是它的**。」 |

### ADR-03 · 为什么选 18–28 岁独居青年，不做银发陪伴

| 项 | 内容 |
|---|---|
| **备选** | A. 银发陪伴 ｜ B. 青少年陪学 ｜ C. 18–28 岁独居青年 ｜ D. 二次元角色向 |
| **选择** | **C** |
| **理由**（对照三原则） | ① **技术可满足**：核心诉求是"有人听"，纯文本可满足；银发群体核心诉求含"陪吃饭、跌倒监测"，必须硬件<br>② **付费链路**：年轻人自己决策、自己付费；青少年付费方是家长，决策链长；银发群体支付能力在子女手里<br>③ **可触达**：小红书/抖音/B站 高度聚集，"深夜 emo""电子布洛芬"是现成流量词；银发群体线上触达成本极高 |
| **代价** | ① 年轻人**付费意愿最低、churn 最高**——这是这条路线最大的风险<br>② 反过来说，银发群体才是长期天花板更高的市场 |
| **重估条件** | V2 付费转化 < 3% 时，说明"年轻人有需求但不肯付"，需重新评估银发/家庭付费模式 |
| **面试怎么讲** | 「我选年轻人不是因为这个市场最大，是因为它**最适合冷启动**——技术门槛低、链路短、触达便宜。代价我清楚：年轻人最不肯付钱。所以我把'付费'放到 V2 验证，V1 只验证需求真不真。」 |

### ADR-04 · 为什么不做心理测评 / 不做诊断

| 项 | 内容 |
|---|---|
| **备选** | A. 做轻量心理测评（如 PHQ-9 简化版）引流 ｜ B. 完全不做诊断 |
| **选择** | **B** |
| **理由** | ① **资质**：心理测评量表虽公开，但"解释结果"属专业行为，无资质做解读<br>② **后果不对称**：做对了没多少收益，做错了是害人。用户拿"中度抑郁"的 AI 结论当诊断，可能延误就医<br>③ **产品定位冲突**：一旦涉及诊断，产品就从"搭子"变成"医疗工具"，触发完全不同的监管要求 |
| **代价** | ① 失去一个引流钩子和付费点 ② 用户主动问"我是不是抑郁"时只能挡回去，体验上有"没用"的感觉 |
| **重估条件** | 不做。这条不重估——**除非有持证专业人员参与设计并在合规框架下运营** |
| **补充** | 用户拿网上量表结果来问时（"我测出来中度"），不能只挡，必须解释"量表不能替代诊断"+ 引导就医。见 `docs/05` §6.1 难例 |

### ADR-05 · 为什么先做记忆，而不是先做主动关怀

| 项 | 内容 |
|---|---|
| **备选** | A. 先做主动关怀（3 天没来就推送）｜ B. 先做长期记忆 ｜ C. 两个一起做 |
| **选择** | **B** |
| **理由** | ① **主动关怀的前提是记忆**：要推"你上次说要面试，加油"必须先记得这件事。没有记忆的主动关怀只是一句群发<br>② **风险程度不同**：主动关怀做不好就是骚扰，会直接伤害留存和口碑；记忆做不好只是"它不记得我"，是渐进式的失望<br>③ **技术依赖顺序**：关怀依赖后台任务 + 记忆系统，记忆是前置 |
| **代价** | 没有主动触点，用户流失时无法挽回——这是 V1 留存偏低的已知原因 |
| **重估条件** | V1.5，在记忆召回率 ≥ 80% 之后 |
| **面试怎么讲** | 「主动关怀听起来很美，但它是记忆的下游。没有记忆的'你上次说…'是编的，而'编造记忆'在我的产品里是一票否决项。所以我宁可先不推，也不推假的。」 |

### ADR-06 · 为什么温度设 0.8，不设 0

| 项 | 内容 |
|---|---|
| **备选** | A. temp=0（稳定可复现）｜ B. temp=0.7–0.9 ｜ C. temp=1.2+ |
| **选择** | **B（0.8）**，分类节点则用 0 |
| **理由** | ① 陪伴产品**最怕可预测**：每次都是同一句"我在"，三轮就腻，temp=0 会强化这种机械感<br>② 但也不能太飘：>1.0 时容易跑题、语气失控、说教<br>③ **分节点设温度**：分类/复检节点要确定性 → 0；主生成要人味 → 0.8 |
| **代价** | 输出不可复现，回归测试需要"批量 + 人工判读"，无法断言字符串相等 |
| **重估条件** | 若人格一致率不达标，先降 temp 到 0.6 观察是否为随机性导致，再决定是否加 Few-shot |
| **面试怎么讲** | 「温度不是全局参数，是**按节点设的**。分类要 0，因为我要可复现；生成要 0.8，因为陪伴产品最怕的就是'每次都是同一句话'。同一个产品里两种温度是正常的。」 |

### ADR-07 · 为什么记忆阈值定 0.7，不是更低

| 项 | 内容 |
|---|---|
| **备选** | A. 0.5（召回高，容易显得"懂你"）｜ B. 0.7 ｜ C. 0.85（极保守） |
| **选择** | **B** |
| **理由** | ① **编造记忆是一票否决**：阈值低 → 把不相关的记忆硬塞进上下文 → 模型顺杆爬编故事<br>② 0.5 时实测（原型阶段）会频繁出现"你之前说…"接错话题，破坏信任<br>③ 0.85 时几乎什么都想不起来，等于没有记忆 |
| **代价** | 该记住的偶尔记不住——用户会觉得"它有点笨" |
| **我的取舍** | **宁可显得笨，也不能显得虚伪**。记不住是可修复的失望，编造是不可逆的失信 |
| **重估条件** | 用真实评测集测出"漏召回率 > 30%"时，改成 0.65 并加**二段重排**（先紧后松） |
| **面试怎么讲** | 「这个阈值的选择本质上是个产品取舍：**记不住 vs 记错**。我选记不住。因为它最多让人觉得它笨，而记错会让人觉得它在骗你。」 |

### ADR-08 · 为什么不用微调

| 项 | 内容 |
|---|---|
| **备选** | A. 现在就微调固化人格 ｜ B. 不微调，提示词 + RAG |
| **选择** | **B** |
| **理由** | ① **没有数据**：微调需要几千条高质量对话，V1 阶段一条都没有<br>② **没有验证**：还不知道人格应该长什么样，微调等于把错误固化<br>③ **成本**：微调有训练成本 + 运维成本，日均调用量不够时无法摊销 |
| **代价** | 提示词方案的人格一致性有天花板，长提示词还占用上下文和成本 |
| **重估条件** | ① 日均对话量过万 ② 提示词 + Few-shot + 后处理都用尽后人格一致率仍 < 85% ③ 有 ≥ 3000 条人工标注过的优质对话 |
| **面试怎么讲** | 「微调不是先进技术的象征，是**成本优化手段**。在还不知道产品该长什么样的时候微调，是把错误焊死。顺序应该是：提示词 → Few-shot → 输出后处理 → 攒数据 → 微调。」 |

### ADR-09 · 为什么评测集用 120 例，不是 500 例

| 项 | 内容 |
|---|---|
| **备选** | A. 20 例（快速迭代）｜ B. 120 例 ｜ C. 500+ 例 |
| **选择** | **B** |
| **理由** | ① **20 例测不出分布**：8 个子场景，平均每场景 2.5 例，测不出任何一类的问题率<br>② **500 例跑不动**：一轮全量评测 = 500 次调用 ≈ 2–3 小时 + 明显成本，**迭代频率会掉到一周一次**<br>③ **120 例的分布**：8 场景 × 3 难度 × 安全类加权，能覆盖主要问题类型，单轮评测控制在 30 分钟内 |
| **代价** | 覆盖不了长尾，某些罕见表达测不到 |
| **补充机制** | ① 长尾靠**线上 Badcase 回收**补（每月把新发现的 badcase 加入评测集）② 安全类单独扩到 24 例，权重 10 |
| **重估条件** | 迭代进入稳定期（每周都跑）后扩到 300 例 |
| **面试怎么讲** | 「评测集不是越大越好。500 例跑一轮要 3 小时，结果就是**一周只能迭代一次**。我要的是**每改一次 prompt 都能在 30 分钟内知道好坏**，所以我选了 120 例，把长尾交给线上 badcase 回收。」 |

### ADR-10 · 为什么把"记忆写入"做成异步

| 项 | 内容 |
|---|---|
| **备选** | A. 同步写（当轮写完再回复）｜ B. 异步写（回复后再写） |
| **选择** | **B** |
| **理由** | 同步写会让每轮延迟 +1.5s 左右，而记忆**晚一轮生效用户完全感知不到**。<br>延迟高 1.5s，用户立刻觉得"卡"；记忆晚一轮，用户毫无感觉 |
| **代价** | ① 用户当轮说"记住我叫小明"，AI 当轮不一定会叫，可能显得迟钝<br>② 异步任务丢失 → 记忆缺失，需要重试 + 对账 |
| **缓解** | 用户显式要求记忆时（"记住这个"），走**同步高优先级**写入 |
| **面试怎么讲** | 「这是典型的**用户感知不对称**：延迟是立刻能感觉到的，记忆晚一轮感觉不到。所以我把它放异步。但有个例外——用户明确说'记住这个'的时候要同步写，因为那是**对产品的一次承诺**。」 |

### ADR-11 · 定位从「急救」改成「第三空间」

| 项 | 内容 |
|---|---|
| **备选** | A. 夜间情绪低谷的陪伴（急救框架）｜ B. 深夜第三空间 / 夜间仪式（仪式框架） |
| **选择** | **B** |
| **理由** | ① **人群规模**："每晚睡前会刷手机的人"远多于"正在情绪低谷的人"<br>② **频率**：急救是周级，仪式是日级；**关系感来自频率，不来自深度**<br>③ **危机位置**：急救框架下危机是核心场景（合规压力最大、对标热线）；仪式框架下危机是**必须兜住的底线**，不再是卖点<br>④ **对标物**：和心理咨询比永远不够专业；和深夜电台比，要的是氛围与可预期，这是能赢的 |
| **外部依据** | Steam 同类产品（Coffee Talk / VA-11 HALL-A）玩家给好评的理由不是剧情，而是"一个深夜可以去待着的地方""够了就关"。**玩家明知玩法单薄仍给好评**，说明这个品类的价值不在内容量 |
| **代价** | ① 日活高但付费意愿可能低（陪伴类通病）<br>② 可能被当成"陪聊"，价值感弱<br>③ **风险最高的一条**：竞品有音乐、美术撑氛围，我们只有文字——氛围必须由对话节奏承担 |
| **重估条件** | 若 H5（"有人愿意每晚来"）验证失败，退回工具定位 |
| **面试怎么讲** | 「原定位听起来合理，但它是急救框架——只吸引正在出问题的人，频率是周级，还要跟心理咨询比专业。我去看 Steam 上同类产品为什么火，玩家说的不是剧情好，是'可以待着'。所以我把它改成第三空间。」 |

> 完整论证见 `docs/16_产品定位_第三空间.md`。

## v5 新增决策（ADR-12 至 ADR-17）

> 以下决策对应 v5.0（2026-11-02）与 v5.1（2026-11-10）。代码位置写在每条末尾，改代码时同步改这里。

### ADR-12 · 主动关怀只基于"用户说过的具体事"，并且先做 A/B

| 项 | 内容 |
|---|---|
| **备选** | A. 定时推送（"今晚想聊聊吗？"）｜ B. 只在用户说过有日期的事时推送，内容引用原话 ｜ C. 不做推送 |
| **选择** | **B，且只对 A/B 实验 `nudge_v1` 的 nudge 组开放**，control 组永远不推 |
| **理由** | ① JD 要求"主动互动与召回"，完全不做不现实；② 泛泛的"想你了"类推送是在利用孤独感，和产品原则冲突；③ 深夜产品的通知本身可能打扰休息，必须用数据证明利大于弊 |
| **护栏** | 用户手动开启；一天最多一条；不申请精确闹钟权限；文案禁止任何愧疚话术 |
| **怎么判断** | `ab_nudge` 查询：两组 D7 留存 **和** 关闭通知数一起看。留存涨了但关通知的人也明显变多，不算赢 |
| **代码** | `server.js` `/v1/nudge`、`tide_core.js` `careNudge`、`CareNotifier.kt` |

### ADR-13 · v5 从"用户自带 Key 直连厂商"改为"服务端代理"

| 项 | 内容 |
|---|---|
| **备选** | A. v3 方案：用户在手机里填自己的 API Key ｜ B. 潮汐自己的服务端代理模型调用，用户无需配置 |
| **选择** | **B**（v3 的直连代码保留为单元测试参考，JS 桥已在 v5.1 从外壳下线） |
| **理由** | ① 海外普通用户不会去申请 API Key——自带 Key 只适合极客，等于放弃大众市场；② 不经过服务端就做不了额度、订阅、埋点、记忆、A/B，JD 要求的指标体系无从谈起；③ 提示词放服务端，人格和安全规则才不会被绕过 |
| **代价** | 要部署和运维服务器；用户数据经过我们（隐私责任变大）；模型成本由我们承担（见 `docs/07` v5 一节） |
| **代码** | `server/`、`TideApi.kt` |

### ADR-14 · Plus 每日 300 轮暂不下调，设监控阈值

| 项 | 内容 |
|---|---|
| **背景** | 按 DeepSeek 官方高峰价保守估算，Plus 用户"天天用满 300 轮"时月成本约 $8.61，高于净收入 $6.79（`docs/07` v5 §3） |
| **选择** | 暂不改；上线后监控 |
| **理由** | 没有数据证明有人这样用；为极端情况提前降额度会伤害正常用户 |
| **触发条件** | Plus 用户日轮次 P95 > 150，或单个 Plus 用户月成本 > $4 → 改为"每日 150 轮 + 超出降速"的合理使用条款 |
| **代码** | `tide_core.js` `PLANS`；监控：`analytics/queries.sql` 的 `usage_tier`、`cost` |

### ADR-15 · 记忆检索暂用"关键词 + 同义词表"，不上向量库

| 项 | 内容 |
|---|---|
| **评测** | `tools/rag_eval.js`（自建 36 例）：加同义词表后调参集 67%→100%，**留出集 33%→50%**，中性句误召回 0/5 |
| **选择** | 保留关键词路线，加 14 组同义词 |
| **理由** | 每人几十条短句的量级下，关键词检索零成本、离线可用、可解释；留出集 50% 说明它有明显天花板 |
| **换向量检索的条件** | 任一：单人记忆中位数 > 500 条；留出集持续 < 70% 且失败主要来自同义/跨语言；"它不记得我说过的事"成为用户反馈 Top 3 |
| **代码** | `tide_core.js` `retrieve` / `ALIASES`；详见 `docs/26` |

### ADR-16 · "能用规则保证的，不交给模型"：补回记忆陷阱与敷衍重生成

| 项 | 内容 |
|---|---|
| **背景** | v5.0 改服务端架构时丢了 v4 的两道规则。`tools/test_model.js` 用本机 qwen2.5:3b 实测出两个坏例：对"今天有点空"只回「嗯。」；系统提示词写着"你什么都不记得"，仍回答"记得，哪家医院呢？" |
| **选择** | 两道规则放回**共享核心**，服务端和离线兜底共用 |
| **理由** | 提示词是"请求"，模型可以不听；编造记忆对陪伴产品伤害极大（像朋友把你妈妈的病记成你爸爸的） |
| **代价** | 记忆陷阱可能误拦（问法里有个巧合的字就放行，没有就拦）；重生成增加 token 成本——用 `retries` 埋点监控 |
| **代码** | `tide_core.js` `recallMiss` / `generateReply`；测试 `server/guard_test.js` |

### ADR-17 · v5 首发 6 个角色（v4 有 12 个）

| 项 | 内容 |
|---|---|
| **选择** | 首发 6 个中英双语角色，v4 的另外 6 个暂不上 |
| **理由** | ① 新手引导是"一个问题 → 推荐一个角色"，角色越多推荐越难解释；② 每个角色都要中英两套人格并分别测试，12 个的测试和人评成本翻倍；③ 先看 `segments` 查询里各角色的激活与留存，再决定加哪类角色 |
| **v5.1 补充** | 角色卡加一句示例台词（`sample`），**只用于展示，不进提示词**（避免 v3 的照抄事故） |
| **代码** | `tide_core.js` `PERSONAS` / `ONBOARD` |

### ADR-18 · v6 从"服务端 + 登录"改为"下载即用、模型在手机上"

| 项 | 内容 |
|---|---|
| **选择** | 去掉服务端与登录，APK 内置 Qwen2.5-1.5B（Q4_K_M，Apache-2.0），在手机上推理 |
| **理由** | ① 面试场景要"发给面试官就能打开"，服务端没部署、登录要账号、Key 要自己配，三步里任何一步失败都看不到产品；② 端侧推理不联网，隐私叙事可以直接讲；③ v5 的慢主要来自"每一步都先等服务端超时"（`docs/31` §1 有实测根因） |
| **代价（如实）** | ① 模型只有 1.5B，理解力不如云端大模型，提示词和输出守卫要更厚；② APK 约 951 MB，下载门槛高；③ 真机速度未测，模拟器数字不能代表手机；④ 图片理解、AI 实时语音只能推迟到 V1.1 |
| **为什么不是"云端 + 降级"** | 做过（v5 就是），降级路径本身就是"连不上时等 10 秒"，体验最差的那条路恰好最常被走到 |
| **代码** | `android/app/src/main/cpp/orbit.cpp`、`src/app/js/02_engine.js` |

### ADR-19 · v6.3 的玩法只取机制、不取角色与文案

| 项 | 内容 |
|---|---|
| **选择** | 从用户提供的恋爱游戏 PRD 里只取"抓娃娃 / 一起专注 / 共同记录 / 有节制的邀请"这些机制，角色、台词、立绘、抽卡一律不做 |
| **理由** | ① 抽卡与长剧情依赖持续运营和付费，和"下载即用、不施压"冲突；② 机制是产品结构，可以搬；角色和文案是别人的资产，不能搬；③ 4 个伙伴已经有人格，玩法要服务于"真的和它做过点事"，不是再来一套养成 |
| **落地时改掉的 PRD** | 她抓完自动结算、她的抓从爪子位置往下而不是瞬移、她第一抓必中、没有历史绝不邀请——理由见 `docs/32` §2 |
| **代码** | `shared/orbit_play.js`、`src/app/js/10_play.js` |

## 第三部分 · 如果重来，我会怎么改

> 面试常问"这个项目有什么遗憾"。照实说，但要说清"为什么当时只能这样"。

| # | 遗憾 | 当时为什么这样 | 现在会怎么做 |
|---|---|---|---|
| 1 | 先写方法论文档，后才跑真实评测 | 从课程笔记出发，习惯先"学"后"做" | **反过来**：先跑 20 条真实 case，再写方法论。没有数据的文档都是猜想 |
| 2 | 用规则引擎冒充"提示词迭代" | 为了做一个能离线演示的 Demo | Demo 只做交互原型，模型能力必须用真实 API 证明。**两者不能混为一谈** |
| 3 | 没有做用户访谈 | 假设"我自己就是目标用户" | 至少访谈 10 人。**自己的直觉不能代替证据**，哪怕你在目标人群里 |
| 4 | 单位经济算错（1200 vs 2040 token） | 两个数字在不同文档里各自写的 | 所有数字只维护**一处**（单一数据源），其他文档引用不重复计算 |
| 5 | 评测集造好了才开始想指标 | 顺手先把 case 写完了 | 先定指标口径，再写 case。**否则 case 无法映射到指标** |

| 为什么记忆优先 | ADR-05 | 主动关怀是记忆的下游 |

| 为什么要自己的服务端 | ADR-13 | 普通用户不会填 Key；没有服务端就没有额度、订阅、埋点 |

| 最大遗憾 | 第三部分 | 先说"先写文档后跑数据"，最诚实 |
