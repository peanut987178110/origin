## 1. 为什么需要工作流：把不确定拆成确定的小步骤

### 1.1 一个超级 Prompt 的问题

```
❌ 一个 5000 字的 Prompt 想搞定一切
   → 不可控：改一处坏三处
   → 不可观测：输出不好不知道哪一步出问题
   → 不可优化：没有单点可以调
   → 不可协作：团队没法分工
```

### 1.2 工作流的价值

```
✅ 每一步只做一件事，单点可测、可优化
✅ 中间结果可见，Badcase 能精确定位到节点
✅ 关键步骤可以用规则而非模型（成本 + 确定性）
✅ 可以插入人工审核、降级兜底
```

### 1.3 工作流 vs Agent（面试必考题）

| | 工作流 Workflow | 智能体 Agent |
|---|---|---|
| **适用** | 步骤固定、确定性要求高 | 步骤未知、需要自主规划 |
| **例子** | 订单查询、风控审核 | "帮我研究这个行业并写份报告" |
| **优点** | 可控、可观测、成本低 | 灵活、能处理开放任务 |
| **缺点** | 覆盖不了没预设的情况 | 不可控、成本高、易跑偏 |
| **本质** | 人设计的流程 | 模型自己决定下一步 |

> **满分答案**：
> "纯靠模型自主规划，在今天的可控性和成本上都撑不起一个 To C 产品；
> 纯工作流又覆盖不了开放场景。
> 我的做法是**工作流做骨架，Agent 做关节**：
> 主链路（安全识别 → 情绪分类 → 记忆检索 → 生成 → 复检）是固定工作流，
> 保证可控可观测；
> 在'生成'这个节点内部，允许模型自主决定要不要调工具、调哪个工具。
> 随着某个子场景的 Badcase 收敛，我会把它从 Agent 节点固化成工作流节点。"

## 2. 「潮汐」主链路工作流设计

### 2.1 全景图

```
                        ┌─────────────┐
                        │  ① 开始     │  用户输入 + user_id + 时间戳
                        └──────┬──────┘
                               ▼
                        ┌─────────────┐
                        │ ② 硬规则     │  敏感词表 / 未成年人标识
                        │   前置过滤   │  （代码节点，不走模型）
                        └──────┬──────┘
                               ▼
                        ┌─────────────┐
                        │ ③ 安全分类   │  LLM 结构化输出
                        │   节点      │  risk: normal|concern|crisis|illegal
                        └──────┬──────┘
                               ▼
                     ┌─────────┴─────────┐
                     │   ④ 条件分支      │
                     └──┬─────┬──────┬───┘
            crisis ◄────┘     │      └────► illegal
               ▼              │               ▼
      ┌────────────────┐      │      ┌────────────────┐
      │ ⑤A 危机干预     │      │      │ ⑤C 硬拦截回复   │
      │  + 热线资源     │      │      │  （固定模板）   │
      │  + 转人工       │      │      └────────────────┘
      └───────┬────────┘      │
              │        normal │ concern
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑥ 情绪与意图识别 │  JSON:
              │      │                 │  emotion/intensity/need
              │      └────────┬────────┘
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑦ 记忆检索       │  向量检索 top-3
              │      │  （RAG）         │  + 时间衰减加权
              │      └────────┬────────┘
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑧ 上下文组装     │  人格 + 记忆 + 近期摘要 + 当前输入
              │      └────────┬────────┘
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑨ 主回复生成     │  LLM（可调用工具）
              │      └────────┬────────┘
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑩ 输出复检       │  安全 + 风格 + 长度
              │      └────────┬────────┘
              │               ▼
              │      ┌─────────────────┐
              │      │ ⑪ 输出           │
              └──────┴────────┬────────┘
                              ▼
                     ┌─────────────────┐
                     │ ⑫ 异步：记忆抽取 │  会话结束/N轮后触发
                     │    与写入        │
                     └─────────────────┘
```

### 2.2 节点清单（照这个搭）

| # | 节点名 | 类型 | 输入 | 输出 | 关键配置 |
|---|---|---|---|---|---|
| ① | 开始 | 开始 | `user_input`, `user_id`, `timestamp` | — | 开启会话变量 |
| ② | 硬规则过滤 | 代码 | `user_input` | `hard_hit: bool`, `hard_type` | 敏感词表正则匹配 |
| ③ | 安全分类 | LLM | `user_input` | JSON `{risk, category, confidence}` | temp=0，strict JSON |
| ④ | 条件分支 | 条件 | `risk` | 路由 | 4 分支：crisis/concern/illegal/normal |
| ⑤A | 危机干预 | 模板 + LLM | `user_input` | 干预回复 + 热线 | **固定结构，不可自由生成** |
| ⑤C | 硬拦截 | 模板 | — | 拒答模板 | 纯模板 |
| ⑥ | 情绪识别 | LLM | `user_input`, `history_summary` | JSON `{emotion, intensity, need}` | temp=0 |
| ⑦ | 记忆检索 | 知识检索 | `user_input`, `user_id` | `memories[]` | top_k=3，相似度阈值 0.7 |
| ⑧ | 上下文组装 | 代码/模板 | 全部 | `final_prompt` | 控制 token 预算 |
| ⑨ | 主回复生成 | LLM (Agent) | `final_prompt` | `reply` | temp=0.8，可调用工具 |
| ⑩ | 输出复检 | LLM | `reply` | JSON `{safe, style_ok, score}` | temp=0 |
| ⑪ | 结束 | 结束 | `reply` | — | — |
| ⑫ | 记忆写入 | LLM + 存储 | 本轮对话 | `memory_record` | **异步执行，不阻塞回复** |

> 完整版见 `workflow/情绪陪伴主链路_节点清单.md`

### 2.3 为什么要"异步写记忆"

```
同步写：用户说 → 识别 → 检索 → 生成 → 写记忆 → 回复
        ⏱ 延迟 +1.5s，用户觉得 AI 变笨了

异步写：用户说 → 识别 → 检索 → 生成 → 回复
                                    └→ (后台) 写记忆
        ⏱ 延迟不变，记忆下一轮生效即可
```

**产品判断**：记忆晚一轮生效，用户完全感知不到；但延迟高 1.5 秒，用户立刻觉得卡。

## 3. 结构设计：RAG / Function calling / MCP / Skill

### 3.1 四者的关系（一张图讲清）

```
                  ┌──────────────────────┐
                  │    大模型（大脑）      │
                  └───────┬──────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   【给知识】         【给动作】         【给能力】
      RAG          Function calling      Skill
   检索外部信息      调用外部工具       可复用能力包
        │                 │                 │
        │                 └──────┬──────────┘
        │                        ▼
        │                      MCP
        │               （工具/数据的统一接口）
        ▼                        ▼
   知识库/记忆库            外部系统 API
```

### 3.2 RAG 在「潮汐」里的特殊用法

**关键认知**：
> 陪伴产品的 RAG，检索的不是"文档"，是**"关于这个用户的记忆"**。

| 传统 RAG | 陪伴产品的记忆 RAG |
|---|---|
| 检索公司文档 | 检索"用户说过的事" |
| chunk = 文档片段 | chunk = 一条记忆卡片 |
| 追求准确 | 追求**相关性 + 新鲜度** |
| 静态知识 | 动态增长 |

**RAG 三步：切 → 存 → 取**

```
① 切（Chunking）
   记忆卡片 = 一条独立事实，不切分，本身就是最小单元
   例：「2026-10-28 用户说养了一只叫橘子的猫」

② 存（Indexing）
   向量化 + 存向量库；同时存结构化字段：
   { user_id, type, content, emotion, time, importance, source_quote }

③ 取（Retrieval）
   向量召回 top-10 → 重排 → 过滤（相似度阈值）→ 取 top-3
   加权：final_score = 0.6×相似度 + 0.25×新鲜度 + 0.15×重要度
```

### 3.3 记忆 Schema（设计文档核心）

```json
{
  "memory_id": "mem_20261028_001",
  "user_id": "u_12345",
  "type": "person | event | preference | emotion_trigger | routine",
  "content": "养了一只叫橘子的猫",
  "entities": ["橘子(猫)"],
  "emotion_tag": "happy",
  "importance": 3,
  "timestamp": "2026-10-28T23:14:00+08:00",
  "last_accessed": "2026-10-30T22:40:00+08:00",
  "access_count": 4,
  "source_quote": "我家那只猫，叫橘子，今天又把我杯子推下去了"
}
```

**记忆写入规则（重要）**：

| 写 | 不写 |
|---|---|
| 用户主动提到的人和事 | 用户的情绪本身（会变） |
| 稳定的偏好、习惯 | 一次性的吐槽 |
| 重要时间节点（面试、考试、分手） | 对话中的角色扮演设定 |
| 反复出现的困扰 | 用户明确说"别记了" |

**记忆遗忘机制**：
```
importance 低 + 30 天未访问 → 归档
用户主动删除 → 立即清除
同一实体新信息 → 更新而非新增
```

### 3.4 Function calling：让模型"说要调什么"

**原理**：
```
模型不自己执行，只输出：「我要调用 get_weather(city="杭州")」
程序执行 → 把结果喂回模型 → 模型生成最终回复
```

**「潮汐」的 6 个工具**（完整定义见 `workflow/外部工具_Function定义.json`）：

| 工具 | 用途 | 触发场景 |
|---|---|---|
| `get_weather(city)` | 查天气 | 闲聊、出门提醒 |
| `play_sleep_content(type)` | 播放白噪音/睡前故事 | 失眠 |
| `save_mood_entry(mood, note)` | 存心情日记 | 情绪高点/低点 |
| `get_user_memory(query)` | 主动检索记忆 | 需要回忆时 |
| `get_crisis_resource(region)` | 获取当地心理援助热线 | 危机分支 |
| `schedule_checkin(time, reason)` | 预约后续关怀 | 重要事件后 |

### 3.5 MCP：为什么需要它

```
❌ 没有 MCP：
   每个模型 × 每个工具 = N × M 次对接

✅ 有了 MCP：
   每个模型 × 1 个协议 + 每个工具 × 1 个协议 = N + M 次对接
```

> **面试话术**："MCP 解决的是工具生态的碎片化问题。我们产品里接入了天气、
> 日程、内容播放三类外部能力，用 MCP 统一声明之后，换模型不用重写对接。"

### 3.6 Skill 与 Agent 的关系

```
Agent  = 大脑（会判断、会规划、会调度）
Skill  = 能力包（一个定义好的、可复用的做事方法）

Skill 三要素：
  ① 触发条件（什么时候用）
  ② 执行步骤（怎么做）
  ③ 输出规范（做成什么样）
```

**「潮汐」的 Skill 设计**：

| Skill | 触发条件 | 步骤 | 输出规范 |
|---|---|---|---|
| `倾听` | 用户情绪强度 ≥ 6 且无明确求助 | 复述事实 → 命名情绪 → 邀请多说 | ≤ 3 句，1 个问题 |
| `陪伴入睡` | 提及"睡不着/失眠" 且时间在 22:00–06:00 | 接纳 → 提供放松/故事选项 → 降低刺激 | ≤ 2 句，不提问 |
| `回忆` | 用户问"你还记得…" | 检索记忆 → 命中则引用+时间；未命中则明说 | 必须带时间或明说不知道 |
| `危机干预` | risk = crisis | 表达在乎 → 不给建议 → 给热线 → 建议联系真人 | 固定四段结构 |
| `边界拒绝` | 医疗/法律/投资/违法请求 | 说明边界 → 给替代方向 | 温和但明确 |

### 3.7 微调：什么时候才需要（面试常问）

```
❌ 现在就需要微调吗？→ 不需要

微调的三个真实触发条件：
  ① 风格固化：提示词已经很长，但人格一致性仍不达标
              （我们的解法顺序：提示词 → Few-shot → 输出后处理 → 微调）
  ② 成本压缩：用微调小模型替代大模型，降 70% 成本
              （前提是日均调用量足够大，摊销训练成本）
  ③ 领域知识：需要模型"长在脑子里"的知识
              （陪伴场景基本不需要）

→ 结论：先 RAG + 提示词跑通，等日均对话量过万、人格一致性仍是瓶颈时再微调
```

## 4. 非功能需求（别漏，面试能说这个很专业）

| 维度 | 指标 | 目标 |
|---|---|---|
| **延迟** | 首字返回时间（TTFT） | ≤ 1.2s（P90） |
| **延迟** | 完整回复时间 | ≤ 4s（P90） |
| **成本** | 单轮对话成本 | ≤ ¥0.006 |
| **可用性** | 服务可用率 | ≥ 99.5% |
| **安全** | 危机识别召回率 | ≥ 99%（宁可误报不可漏报） |
| **安全** | 危机识别精确率 | ≥ 90% |
| **降级** | 模型超时/失败 | 3s 后返回兜底温暖回复 |
| **合规** | 未成年人 | 识别后情感陪伴功能降级 |
