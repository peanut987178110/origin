# 13 · 数据埋点与指标字典

> `docs/06` 定了指标，`workflow/节点清单` §4 列了埋点事件，
> 但两者**没有对上**——一个是"我们要看什么"，一个是"我们要记什么"，
> 中间缺了一层：**每个指标由哪个事件、哪个字段算出来。**
>
> 这份字典补的就是这一层。面试官问"这个指标怎么统计"，答案在这里。

---

## 一、埋点设计的三条原则

| 原则 | 说明 | 反面例子 |
|---|---|---|
| **指标先行** | 先定指标，再定事件。没有对应指标的埋点不要埋 | "先把能埋的都埋上"——最后没人用，还拖慢性能 |
| **事件不可变** | 事件一旦上线，字段只加不改 | 改一个字段名，历史数据全部断层 |
| **口径单一** | 每个指标只有一个定义、一个 SQL | "活跃用户"三个团队三种算法 |

> 🔑 **第三条最容易踩坑**：
> 你的 DAU 是按"打开即算"，还是"发过消息才算"？
> 两个口径能差 40%。**必须在文档里写死，并且只有一处**。

## 二、事件字典

### 2.1 事件清单

| 事件名 | 触发时机 | 关键字段 | 服务于哪些指标 |
|---|---|---|---|
| `app_open` | 启动 | user_id, ts, source | DAU、回访率 |
| `message_sent` | 用户发送消息 | user_id, session_id, turn, ts, hour, len, content_hash | 轮次、时段分布、深度表达 |
| `emotion_detected` | 情绪识别完成 | emotion, intensity, intent, confidence | 识别准确率 |
| `pain_attributed` | 归因完成 | pain, confidence, cross_pattern | 归因准确率 |
| `memory_retrieved` | 记忆检索完成 | count, max_score, hit | 召回率、命中率 |
| `memory_written` | 异步写入完成 | type, success, retry | 写入成功率 |
| `risk_detected` | 风险分级完成 | risk, category, confidence, layer | 危机召回/精确率 |
| `crisis_branch` | 进入危机分支 | level(L2/L3), has_hotline | 危机处理完成率 |
| `reply_generated` | 回复生成完成 | ttft_ms, total_ms, in_tokens, out_tokens, model, fallback | 延迟、成本、降级率 |
| `reply_reviewed` | 复检完成 | passed, violations[], retried | 违规漏放率 |
| `session_end` | 会话结束（30 分钟无活动） | turns, duration_min, risk_flag | 会话深度 |
| `feedback` | 用户点赞/点踩 | like, reason_code | 好评率 |
| `memory_deleted` | 用户删除记忆 | scope(one/all), trigger | 隐私履约 |

### 2.2 字段规范

```
user_id     匿名化 ID，不可反查
session_id  一次会话（30 分钟无活动即断）
turn        本会话第几轮
ts          客户端时间戳（毫秒）
hour        服务端计算的 0–23 小时（用于时段分析，避免时区问题）
content_hash 内容哈希（用于去重，不存原文）
```

> ⚠️ **注意 `hour` 用服务端计算**：客户端时间可能被篡改，
> 而时段分布是 H4 的验证依据，不能错。

## 三、指标字典

> 格式：定义 → 计算口径 → 目标【目标值】 → 归属假设 → 埋点来源

### 3.1 技术指标（能不能用）

| 指标 | 计算口径 | 目标 | 来源事件 |
|---|---|---|---|
| **安全通过率** | 安全类用例通过数 / 安全类用例总数 | **100%**（一票否决） | `risk_detected` + 评测 |
| **危机召回率** | 真危机中被识别为 crisis 的比例 | **100%** | `risk_detected` vs 人工标注 |
| **危机精确率** | 判为 crisis 中确实是危机的比例 | ≥ 90%【目标】 | 同上 |
| **编造记忆率** | 回复中引用了记忆库不存在内容的次数 / 引用总次数 | **0**（一票否决） | 人工抽检 `memory_retrieved` + 回复 |
| **情绪识别准确率** | 与人工标注一致 / 标注总数 | ≥ 85%【目标】 | `emotion_detected` vs 标注 |
| **归因准确率** | 与人工标注一致 / 标注总数 | ≥ 80%【目标】 | `pain_attributed` vs 标注 |
| **记忆召回率** | 应被检索到的记忆中实际检索到的比例 | ≥ 80%【目标】 | `memory_retrieved` vs 预设 |
| **JSON 解析成功率** | 解析成功 / 总调用 | ≥ 99% | 分类节点日志 |
| **TTFT P90** | 首字返回时间 90 分位 | ≤ 1.2s【目标】 | `reply_generated.ttft_ms` |
| **完整回复 P90** | 总响应时间 90 分位 | ≤ 4s【目标】 | `reply_generated.total_ms` |
| **单轮成本** | (in_tokens × 单价 + out_tokens × 单价) 均值 | ≤ ¥0.006 | `reply_generated` |
| **降级率** | 走兜底模板的轮次 / 总轮次 | ≤ 2% | `reply_generated.fallback` |

**统计口径的坑（必须写清）：**
```
❌ "平均延迟"  → 被少数极慢请求拉高，看不出常态
✅ "P90 延迟"  → 90% 的用户体验在此之内，才是真实体感

❌ "安全通过率 98%"  → 听起来不错，实际意味着每 50 次就有 1 次漏判
✅ "安全类一票否决"  → 安全不能用平均率衡量
```

### 3.2 产品指标（用户认不认）

| 指标 | 定义 | 目标 | 归属假设 | 为什么用这个 |
|---|---|---|---|---|
| **深度情绪表达占比** | 含负面情绪且长度 > 30 字的用户消息 / 用户消息总数 | ≥ 20%【目标】 | **H1** | 直接测"愿不愿说真话"，比"消息数"准确 |
| **人均对话轮次/天** | 用户消息数 / 活跃用户数 | ≥ 12【目标】 | H1 | 关系深度的代理指标 |
| **24h 回访率** | 次日打开且有对话的用户 / 当日用户 | ≥ 40%【目标】 | — | 早期留存信号 |
| **夜间回访率（北极星）** | 22:00–02:00 访问后次日再来的用户 / 当日用户 | ≥ 40%【目标】 | **H5** | 第三空间定位的生死线 |
| **连续来访天数** | 连续 3 天 / 7 天有对话的用户占比 | 3 天 ≥ 25%【目标】 | **H5** | 关系感来自"每晚都在" |
| **平均停留时长** | 单次会话分钟数 | 6–12 分钟【目标】 | — | ⚠️ 过长为警报，可能是危机 |
| **记忆触发回访率** | 收到记忆相关回复后再次访问的用户占比 | ≥ 15%【目标】 | **H2** | 直接测"记忆是否制造了价值" |
| **主动回访率** | 收到关怀推送后返回的比例 | ≥ 15%【目标】 | H2 | V1.5 才有 |
| **好评率** | 点赞 / (点赞+点踩) | ≥ 60%【目标】 | H3 | 单轮满意度 |
| **负面反馈率** | 点踩 + 举报 / 总轮次 | ≤ 5% | — | 体验红线 |
| **时段集中度** | 22:00–02:00 消息数 / 总消息数 | ≥ 40%【目标】 | **H4** | 验证夜间定位 |

**最值得投的那个指标：深度情绪表达占比**

> 面试怎么讲：
> 「我不看 DAU，也不先看留存——因为 V1 阶段如果用户只是在问天气，
> 留存再高也没有意义。我第一个要看的是**深度情绪表达占比**：
> 用户到底有没有说真话。
> 这个指标不达标，说明产品还是个工具，不是搭子。
> 它是我判断 H1 成不成立的唯一依据。」

### 3.3 商业指标（赚不赚钱）

| 指标 | 定义 | 目标 | 备注 |
|---|---|---|---|
| **付费转化率** | 付费用户 / 活跃用户 | ≥ 5%【目标】 | V2 才验证 |
| **月 ARPU** | 月度收入 / 付费用户 | ≥ ¥12【目标】 | |
| **单人月 token 成本** | 见下方算例 | ≤ ¥2.6 | 按 2040+200 token |
| **LTV / CAC** | 用户生命周期价值 / 获客成本 | ≥ 3 | 冷启动期通常难看 |
| **年卡占比** | 年卡 / 全部付费 | ≥ 40% | 判断留存策略是否有效 |

**token 成本算例（与 `docs/02`、`docs/07` 同一口径）：**
```
单轮输入 2040 token × ¥2/M   = ¥0.00408
单轮输出 200  token × ¥8/M   = ¥0.00160
                     单轮合计 = ¥0.00568

日均 15 轮 × 30 天 = 450 轮/月
450 × ¥0.00568 = ¥2.56/人/月
```

## 四、指标分层与优先级

```
第一层 · 安全与诚实（一票否决）
  危机召回 100%  ·  编造记忆 0  ·  隐私删除履约 100%
  ↓ 不达标，下面全部不看

第二层 · 能不能用（体验底线）
  TTFT P90 ≤ 1.2s  ·  降级率 ≤ 2%  ·  解析成功率 ≥ 99%

第三层 · 有没有人用（价值验证）
  夜间回访率 ≥ 40%  ·  连续 3 天 ≥ 25%  ·  停留 6–12 分钟

第四层 · 赚不赚钱（商业化）
  付费转化 ≥ 5%  ·  LTV/CAC ≥ 3
```

> 💡 **这个分层本身就是面试答案**：
> 「指标不能只讲一堆数字，要讲**优先级**。
> 我的原则是第一层不达标，第四层再好看也不算成功。
> 一个用户很多但其实没人在说真话的陪伴产品，是数据幻觉。」

## 五、怎么验证假设（指标 ↔ 假设映射）

| 假设 | 对应指标 | 判定标准 | 不达标怎么办 |
|---|---|---|---|
| **H1** 愿不愿说真话 | 深度情绪表达占比 | ≥ 20% | 说明定位偏了，可能是工具而非搭子 → 改引导策略或重审人群 |
| **H2** 记忆是否制造价值 | 记忆触发回访率、有/无记忆 A/B 留存差 | 差 ≥ 8pt | 记忆不是核心价值 → 砍记忆投入，转投别的差异化 |
| **H3** 无评判是否更受欢迎 | 好评率、A/B 轮次差 | 显著 | 说明用户要建议 → 调整意图识别，支持"求建议"分支 |
| **H4** 夜间是否是核心 | 时段集中度 | ≥ 40% | 定位改为"碎片陪伴"，运营时间与推送策略全改 |

> **注意 H3 的"不达标怎么办"**：不是硬扛，是**准备改动产品结构**。
> 假设的价值在于它能让你改，不在于它是对的。

## v5 · 当前实装的事件字典（以代码为准，2026-11-10）

> 上文是 v1 的设计稿，事件名和字段与 v5 代码不完全一致。**v5 以本节为准**。
> 存储：服务端 `events` 表（`device_id, name, ts, props(JSON)`）。客户端事件先攒在内存，满 10 条或 App 切后台时批量上报 `/v1/events`；服务端只接受白名单里的事件名。
> 隐私：**任何事件都不存聊天原文**，只存长度、角色、耗时、token 数等元数据。

### 1. 事件清单

| 事件 | 上报方 | 关键字段 | 何时触发 | 用于 |
|---|---|---|---|---|
| `signup` | 服务端 | country, lang, nudge_v1 | 静默注册成功 | 漏斗起点、A/B 分组 |
| `age_confirmed` | 服务端 | — | 确认 18+ | 漏斗 |
| `onboarding_step` | 客户端 | step(age/question_shown/choice), choice, persona | 新手引导每一步 | 引导选项分析 |
| `persona_browse` | 客户端 | from, matched | 点"换一个陪伴者"看全部角色 | 角色发现：多少人不接受推荐 |
| `persona_selected` | 服务端 | persona, source(onboarding/onboarding_other/settings) | 选定或切换角色 | 漏斗、分群维度 |
| `onboarding_done` | 客户端 | persona | 进入聊天页 | 漏斗 |
| `app_open` | 客户端 | persona | 打开聊天页 | 活跃 |
| `message_sent` | 服务端 | persona, lang, len, turn, recalled, followups, ms, tin, tout, **retries** | 每一轮成功回复 | 激活、留存、成本、敷衍率 |
| `recall_miss` | 服务端 | lang | 记忆陷阱拦截 | 回复质量、记忆需求信号 |
| `crisis_routed` | 双端 | layer(client/server), lang | 危机路由 | 安全、合规年报 |
| `chat_error` | 服务端 | reason | 上游模型失败 | 稳定性 |
| `offline_fallback` | 客户端 | status | 切到手机内置模型 | 稳定性 |
| `memory_extracted` / `memory_extract_failed` | 服务端 | added | 异步抽取 | 记忆质量 |
| `memory_added` / `memory_deleted` | 服务端 | source（仅 added） | 手动添加 / 删除 | 记忆使用；**删除率是"记错了"的信号** |
| `nudge_scheduled` | 服务端 | memory | 排了一条晚间关怀 | 召回链路 |
| `nudge_opened` | 客户端 | — | 从通知点进来 | 召回链路 |
| `nudge_dismissed` | 客户端 | action(disable) | 关闭晚间关怀 | A/B 护栏指标 |
| `return_visit` | 客户端 | gap_days, with_memory, persona | 隔 ≥2 天回来、角色先开口 | 回访承接 |
| `ai_notice_shown` | 客户端 | — | 显示 AI 身份提示 | 合规留痕 |
| `paywall_view` | 双端 | trigger(soft_cap/settings), used | 看到付费墙 | 会员漏斗 |
| `paywall_click` | 客户端 | — | 点"开通" | 会员漏斗 |
| `subscribe` | **仅服务端** | plan, fake | 订阅成功 | 转化。客户端上报的 subscribe 会被丢弃，防止刷转化率 |

### 2. 指标口径（每个指标只有一个定义、一条 SQL）

| 指标 | 定义 | SQL（`analytics/queries.sql`） |
|---|---|---|
| 激活 | 注册后 24 小时内 ≥3 条 `message_sent` | `funnel` |
| Dn 留存 | 注册日后第 n 个 UTC 自然日有 `message_sent`；分母只算注册满 n 天的设备 | `retention` |
| 分群（自报） | 按首个 `persona_selected.persona` 切分的激活与 D1 | `segments` |
| 分群（行为） | 近 7 天有对话的天数：1–2 轻 / 3–5 中 / 6–7 重 | `usage_tier` |
| 周 cohort | 按注册周，第 0–3 周仍有对话的设备数 | `cohort_weekly` |
| A/B | nudge 与 control 的 D7 留存 + 关闭通知数；双比例 z 检验 | `ab_nudge` + `report.js` |
| 召回链路 | 关怀排程 → 点开；回访中带记忆承接的占比 | `recall_loop` |
| 敷衍率 | `retries > 0` 的轮次 ÷ 总轮次 | `reply_quality` |
| 危机转介 | `crisis_routed` 按层计数 | `safety` |
| 成本 | Σ(tin × 输入单价 + tout × 输出单价) | `cost` + `report.js` 的 `PRICE` |

**SQL 正确性怎么保证**：`node --experimental-sqlite analytics/report.js --selftest` 会生成一批"每台设备命运都事先写死"的合成数据，用手算的答案逐项核对 SQL 结果（当前 35 项）。合成数据的报表头会打 `SYNTHETIC` 水印，**这些数字不能出现在任何简历或汇报里**。

### 3. 北极星与护栏

| 类型 | 指标 | 为什么 |
|---|---|---|
| 北极星 | **周有对话夜数**：每个活跃用户每周有 `message_sent` 的自然日数（`usage_tier` 的基础） | 产品定位是"每晚可以来坐坐的地方"（`docs/16`），价值在频率不在时长 |
| 护栏 | 重度层（6–7 天/周）占比与人均轮次 | 过度依赖风险 + 成本（`docs/07` v5、ADR-14） |
| 护栏 | `nudge_dismissed` 关闭率 | 推送不能变成打扰 |
| 护栏 | `memory_deleted` / `memory_extracted` | 删得多 = 记错了 |
| 底线 | `crisis_routed` 每一条都要有记录 | 合规 |

> 为什么北极星不是"使用时长"：时长越长不一定越好。一个人凌晨三点还在跟 AI 聊了两个小时，这可能是产品失败的信号。

## v6 · 当前实装的事件字典（以代码为准，2026-11-15）

> 上面 v5 那一节描述的是服务端版本（`events` 表、批量上报）。**v6 没有服务端**：全部事件只写在本机的 `localStorage`，看板直接读这份本地日志。
> 事件名去重后共 **53 个**（`src/app/js/*.js` 与 `shared/orbit_*.js` 里所有 `track('…')`）。每条都带 `exp`：`[{experiment_id, variant_id}, …]`，即四个实验的分组结果。

### 1. 事件清单（按功能分组）

**引导与角色**

| 事件 | 关键字段 | 何时触发 |
|---|---|---|
| `app_open` | — | 打开 App |
| `onboarding_started` / `onboarding_completed` | variant, character, relation, activity | 进引导 / 引导结束（A/B：`onboarding_order_v1`） |
| `character_selected` | character | 选定角色 |
| `character_configured` | fields[] | 改角色设置（语气、长度、主动程度…） |
| `character_regenerated` | — | 重新生成角色 |

**对话**

| 事件 | 关键字段 | 何时触发 |
|---|---|---|
| `first_message_sent` | character | 第一条消息 |
| `message_sent` | len, lang | 每条用户消息 |
| `conversation_started` / `conversation_completed` | — | 会话开始 / 结束（有摘要） |
| `reply_guarded` | issues[], retried | 守卫拦过东西 |
| `reply_regenerated` | — | 用户手动"重新生成" |
| `quality_fallback` | issues[] | 两次生成都不过守卫，用了兜底话术 |
| `feedback_submitted` | kind, reason | 点赞/点踩 |
| `safety_event_triggered` | kind(self_harm/harm_others/danger) | 危机路由（**不扣额度、不进模型**） |

**记忆**

### 2. 指标口径

| 指标 | 定义 | 实现 |
|---|---|---|
| 周期望 | 每个用户每周有 `message_sent` 的自然日数 | `LIFE.computeMetrics` |
| 激活 | 24 小时内 ≥3 条 `message_sent` | 同上 |
| D1 / D7 | 注册后第 n 个自然日有对话；分母只算满 n 天的用户 | 同上 |
| 有效对话占比 | `conversation_completed` 里"算一次有效对话"的比例 | `isEffective` |
| 回复质量 | `quality_fallback` + `reply_guarded` 的轮次占比 | 看板"回复质量" |
| 玩法 | `activity_completed` ÷ `activity_started`；`relationship_progress` 的触顶比例 | 同上 |
| 会员 | `paywall_viewed` → `trial_started` / `subscription_started` | 同上 |

**看板分两块**：这台手机的**真实本地埋点**，和一组 400 人的**合成演示队列**（`syntheticCohort(400, 7)`，固定种子，标 `SYNTHETIC — NOT REAL USERS`）。两块用同一套 `computeMetrics()`，定义完全一样；区别是合成数据可以随时重置，用来演示"看板怎么读、A/B 怎么比"，**不能引用其任何数字**。

### 3. 北极星与护栏（v6）

| 类型 | 指标 | 为什么 |
|---|---|---|
| 北极星 | 周有对话夜数 | 定位是"每晚可以来坐坐的地方" |
| 护栏 | `proactive_message_dismissed` 连续 3 次 → 自动降频 | 推送不能变成打扰 |
| 护栏 | `memory_deleted` 相对 `memory_candidate_created` | 删得多 = 记错了 |
| 护栏 | `safety_event_triggered` 每一条都要记录 | 合规 |
| 护栏 | `quality_fallback` 占比 | 兜底话术过多 = 模型不够用 |
